# RCA — Drill 01: Elevated 5xx (executed 2026-07-10)

> A **drill** (self-induced), run against a live deployment of this lab and then torn down. Written to the same standard as a real incident RCA.

## Summary

At **17:54:15Z** I injected an application fault (`FORCE_500`) into both app instances, causing every user request to `/` to return HTTP 500 while the health check stayed green. The `cops-alb-5xx` alarm detected it automatically and entered ALARM at **17:57:12Z** — a detection latency of **~2m57s**. I removed the fault at **17:57:47Z**; the service recovered immediately (200s restored, both targets healthy) and the alarm returned to OK at **18:06:12Z**.

## Impact

- **Scope:** 100% of requests to `/` returned 500 for the duration (~3.5 min). Lab only — no real users.
- **Detection:** automated, 177s. No human was needed to notice.
- **Customer-facing SLO:** the availability signal (`cops-alb-5xx`) is the one that paged — i.e. we alerted on the *symptom the user feels*, which is correct.

## Root cause

Deliberately injected: the app returns 500 when `/opt/app/FORCE_500` exists. In a real incident this stands in for a bad deploy or an unhandled application exception on the request path.

## What went well

- The alarm fired on its own, on the customer-facing symptom, with no manual watching.
- **Health-check independence held:** `/health` is decoupled from the user-path fault, so targets stayed healthy and the ALB kept serving (returning the app's real 500s) rather than masking them as ELB 503s. `cops-unhealthy-targets` correctly stayed OK.
- Recovery was a single, reversible action (remove one file) — no redeploy, no state change.

## Detection-latency note

The 177s is dominated by ALB CloudWatch metric-publishing latency (~1–3 min), not by the alarm config. Tightening the evaluation period would not meaningfully beat it; an outside-in synthetic canary (as in the [cloud-observability-sre](https://github.com/Abheenash/cloud-observability-sre) project) is the lever for faster detection if needed.
